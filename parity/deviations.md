# Accepted deviations from Claude Code

A model-visible difference from the baseline is allowed only when noeta's kernel or product
forces it ([ADR 003](../docs/adr/003-claude-code-is-the-model-visible-contract.md)). Each row names the reason;
a backticked id is the `make parity` mismatch it accepts (the comparator does not count it).
A row without an id is a difference the replay cannot see. The last column says what pi
(`badlogic/pi-mono` @ e7a0df27) and dsh (`deepseek-ai/DeepSeek-Harness` @ f3803c96) do for the
same thing.

## Kernel

| id | difference | reason | pi / dsh |
|---|---|---|---|
| | Tools run after the assistant message is logged, not while it streams. | Log-first crash safety. | pi runs tools after the whole reply streamed; its experimental `durable` package commits the reply and its tool jobs before running them. dsh appends the reply to its session log, then executes. |
| | A tool started before a crash answers "result unknown", unless it can tell its own outcome (`Tool.recover`) or is safe to run again (`retry_safe`: it re-runs, a few times at most). | A call may have had effects; running it twice is worse than asking. | pi `durable`: tools marked `replay: "safe"` re-run (limit 5), others answer "was interrupted and may have partially run"; its CLI agent has no crash recovery. dsh: a synthetic end event says the outcome is unknown; nothing re-runs. |
| | Waits (approval, sub-agent, timer) survive restarts and move between machines. | Durable tasks. | pi `durable`: timers and replay-safe sub-agent calls survive restarts, one process per store; no approvals. dsh: reminders are durable; approvals and background jobs live in process memory; no move between machines. |
| `6c773c2c` | The results of one reply's calls go back in call order; Claude Code answered a `ToolSearch` ahead of the background `Bash` call made before it (r2 m5). | Results are logged per call and folded in call order; the order of a batch is the kernel's, not a model-visible rule noeta can see the reason for in the recording. | pi and dsh: results in call order. |
| `e9d39432` | After a compaction Claude Code sends an empty system turn carrying `output_config` (its effort); noeta sends none. | noeta puts the effort in the request's top-level `output_config` on every call, which the comparator already matches; the empty turn carries nothing the model reads. | pi (and dsh, through pi's provider layer): the empty `output_config` system turns where the model takes per-turn effort, as Claude Code; otherwise top-level. |
| | `EnterWorktree` moves the shell (where `Bash` starts) into the worktree; the task's root — the environment note, the file tools' relative paths, the permission scope — stays the launch directory, so a worktree must lie inside it (`.noeta/worktrees/`, or an existing one inside the working directory), and a sandboxed command cannot write there (`.noeta` is read-only in the sandbox). | A task's working directory is its config, fixed for its exec env and its sandbox; changing it mid-task needs a kernel config change (and its confinement rules for servers) left for later. | pi: no worktree tool. dsh: an experimental, off-by-default `create_worktree` moves the whole session's working directory (`.agents/worktrees`). |

## Permissions

| id | difference | reason | pi / dsh |
|---|---|---|---|
| | A `Write` / `Edit` outside the working and additional directories (and the plan and memory directories) is refused, not asked about. | The file tools fence writes below the permission layer, so a host without the permissions plugin stays fenced; a directory is opened with `additionalDirectories`. | pi: no limit (tools run with the process's rights). dsh: refused in `workspace-write` mode, with a hint to ask for more. |
| | "Always" answers in a trusted project are kept in `.noeta/settings.local.json` (Claude Code's format), and `.noeta/` is protected the way Claude Code protects `.claude/`. | noeta reads and writes only its own places (owner, 2026-10-28). | pi: no approvals. dsh: approvals cover one request; no "always". |
| | A rule saved to `.noeta/settings.local.json` ("always" in a trusted project) adds the file to the repository's own `.git/info/exclude` (unless git ignores it already); Claude Code adds `.claude/settings.local.json` to the user's global git excludes file (`core.excludesfile`). Files the person writes through `noeta mcp` or `/config` are left as they are. | The point is the same: the model's `git status` stays clean and `git add -A` does not commit the person's grants. Changing the person's global git configuration from a server worker would reach every repository on that machine and every other user of the account; the repository's exclude list changes only the repository the rule was saved in and travels nowhere. | pi: no saved approvals. dsh: no "always" approvals. |
| | Plan files live in `<noeta home>/plans/`. | noeta's own config directory. | pi: no plan mode. dsh: no plan file; the plan is `exit_plan_mode`'s argument. |
| | `WebFetch` of one of Claude Code's preapproved documentation hosts is asked about per domain like any other; Claude Code lets it through without asking. | Owner question (context audit closure, Q6), still open: a server-side agent's fetches are unattended, and the preapproved list is Claude Code's choice of sites. noeta already returns those sites' markdown as Claude Code does. | pi: no WebFetch. dsh: approvals cover one request; no preapproved hosts. |
| | In a workspace that is not trusted, the auto-mode classifier's instruction block is `<untrusted_instructions>`, introduced as the repository's words that grant no intent; Claude Code always sends its block as the user's (`cls.input.1`). | Claude Code runs only in a folder the person accepted in its trust dialog; a server-side noeta runs tasks in repositories nobody vetted, where a planted `NOETA.md` would otherwise speak for the person to the classifier. Same file text, only the preamble and tag differ. | pi: no classifier. dsh: no classifier; the person approves. |
| | `EnterPlanMode` asks the person in `default` and `acceptEdits` mode; Claude Code asks only in its remote (diskless) sessions and lets a local session enter plan mode without asking. | Settled from the 2.1.312 bundle: its `checkPermissions` asks when the session is diskless and the mode is neither auto nor plan, saying that in plan mode the classifier may approve what the person would otherwise be asked about. Owner question. | pi: no plan mode. dsh: only the person's `/plan` enters plan mode; the model has no tool for it. |
| | Plan mode runs with the auto-mode classifier (`useAutoModeDuringPlan`) only when planning starts from auto mode; a plan begun in any other mode leaves every ask to the person, with no auto-mode betas, no server-side check and no classifier calls. Claude Code uses the classifier for any plan (except one begun from `bypassPermissions`, or with bypass available) whenever its account-level auto-mode gate is open (the account's server-side switch, a supported model, no `disableAutoMode`), whatever mode the plan began in. | noeta has no account gate to stand for "auto mode available", and a person who switched to `default` mode chose to be asked: handing that person's asks to a classifier because the host could run auto mode would quietly approve shell writes on unattended servers, and on a non-Anthropic model add classifier calls that fall back to the main model. The choice is fixed in the plan record when plan mode is entered, as Claude Code fixes it on entry; a planning task's sub-agents follow their parent's record (`plan_origin` in the child's config), not the service's default mode. | pi: no plan mode, no classifier. dsh: no classifier; plan mode refuses writes and the person approves. |
| | A sub-agent that ends without `SubagentHandback` in auto mode gets no end-of-run review: Claude Code then classifies the agent's transcript once more (a `<subagent_hand_back>` message, severity-scored on `claude-sonnet-5`) and puts a security warning above its result. | Its text is not delivered either way (`sub.result.8`), and every action it took was classified when it ran; a second review path (one more classifier call per such agent) is an owner decision. | pi: no classifier. dsh: no classifier. |
| | A classifier transcript too long for its window falls back to the person's ask in every host; Claude Code aborts a headless (no prompts) agent instead. | A noeta host answers asks its own way (a person, `can_use_tool`, a stream client), so the fallback needs no host-specific case; a task nobody answers waits where a supervisor sees it. | pi: no classifier. dsh: no classifier. |
| | The first auto-mode request's `safeguards` context lists the permission rules as plain strings; Claude Code sends each as an object naming its settings source (with the canonical spelling and, for a file rule, its anchor root and pattern) (`cls.input.18`). | A host hands noeta its rule lists already merged (the `Permissions` arguments carry no source), so a source would be made up; with an API key the server only answers that it does not run the check, so nothing reads the field. | pi: no classifier. dsh: no classifier. |
| | Shell paths held to deny rules (`tool.Bash.24`, `tool.Bash.25`) are judged more widely than Claude Code's check, refusing more, never less. (1) A relative path is judged under every directory the command may be in by then (each `cd` or `pushd` it passes, `env -C`, and the one it started in; leaving the working directories does not stop the tracking), so after a `cd` that is not the command's leading `cd <dir> &&` it is refused when covered there; Claude Code checks only absolute paths after such a `cd` and asks about the command, which `bypassPermissions` then lets run. (2) Comments, heredocs (an unquoted one's substitutions), subshells, brace groups and command or process substitutions are read past, and the commands inside are judged; Claude Code asks about a subshell or command group without judging its paths. A command still unreadable (unbalanced quotes) is refused when its text names a covered path. (3) A glob, in a write or a read, is judged by what it expands to in the task's environment (and as written); Claude Code asks about a write glob and judges a read glob by the directory above it, so `cat .e*` passes its `Read(./.env)` check. (4) `xargs`, `sudo` and `doas` are looked through like Claude Code's pass-through programs, and `ln` and `install` are writers (every operand, as `cp`). (5) A recursive `rm` or an `mv` of a directory that holds a path an `Edit` deny rule names (one tied to a place: `./x`, `/x`, `//x`, `~/x`) is refused; Claude Code lets `rm -rf config` remove a denied `config/prod.toml`. (6) The twelve programs Claude Code reads with a per-flag table (`cut`, `paste`, `column`, `tac`, `fold`, `expand`, `unexpand`, `fmt`, `comm`, `cmp`, `pr`, `numfmt`) are read as plain operands, so a flag's value may be judged as a path too. | A deny rule must hold in bypass mode on an unattended server, where Claude Code's asks become runs; each case is a way the same write or read reaches the file. A refusal costs one retry with a plain command; commands that leave covered paths alone are not affected (tested with everyday commands), and nothing is judged when no `Edit` or `Read` deny rule exists. | pi: no permission rules. dsh: no deny rules on shell paths. |

## Sandbox

| id | difference | reason | pi / dsh |
|---|---|---|---|
| | A sandboxed command's connection to a host outside `sandbox.network.allowedDomains` is refused and listed in `<sandbox_violations>`; nobody is asked mid-command (Claude Code prompts unless `strictAllowlist`). | The network filter answers while the command runs; asking would need the task to park inside a running tool call. | | When a sandboxed command's working directory is a linked git worktree (an isolated agent's), its own git directory and the shared repository's `objects`, `refs` and `logs` are writable too, so the agent can commit; the shared `config`, `hooks`, `packed-refs` and the worktree's `commondir`, `gitdir` and `config.worktree` stay read-only.
