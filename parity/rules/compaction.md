## Trigger (auto-compaction, observed in m3)

| id | rule | noeta today |
|---|---|---|
| compact.trigger.1 | Auto-compaction is checked before each main-loop model request, not only at user turns: three of the four m3 compactions fired mid-turn, right after a tool result arrived. | covered — `Compaction.before_model` measures before every model request, mid-turn included. |
| compact.trigger.2 | The estimate is the last response's reported usage (input + cache read + cache write + output) plus the size of what was appended since. With the threshold at ~30K, a 13.5K-token context plus a ~19.8K-token Read result fired (m3/0007→0009); a 40K-token response context fired on the next step even though the newly appended result was tiny (m3/0010→0012). | covered — `_tokens`: the newest reply's reported usage (input incl. cache read/write, plus output) and the estimate of what followed (`estimate.py`). |
| compact.trigger.3 | A large new tool result is measured exactly with `/v1/messages/count_tokens` before the decision (m3/0008, m3/0015: the raw file text of a 1001-line Read, ~79K chars → 19,771 tokens). Small results are not counted that way (no `count_tokens` call anywhere in m1). The bundle places the count in Read's token-ceiling check (`side-requests.md` side.count.3), not in the compaction trigger. | covered — the exact count is `Read`'s token ceiling (`fs/read.py`, `ctx.count_tokens` past a quarter of it); the trigger itself uses the estimate, as the bundle does. |
| compact.trigger.4 | The first request after a compaction is sent even when it is itself over the threshold (m3/0010 and m3/0019 carried ~35K input tokens); the next check, after that response, compacts again. | covered — the first request after a compaction goes as it is until a reply reports usage (`before_model`). |
| compact.trigger.5 | No "context low" warning reminder is sent before an auto-compaction; the next request is simply the compaction request. | covered — no context-low note anywhere in noeta. |
| compact.trigger.6 | The threshold is a fraction of the model's context window (configurable; the recording forced 30 % of a 100K window). The default fraction is not visible in the baseline recordings. | covered — `window.py`: effective window less 13,000, or `NOETA_AUTOCOMPACT_PCT_OVERRIDE` / `auto_compact_percent` when lower; `NOETA_AUTO_COMPACT_WINDOW` caps the window. |
| compact.trigger.7 | Rapid-refill breaker (bundle, not in the recordings): within one user turn, an auto-compaction needed again fewer than 3 model calls after the previous one counts as a refill; at the third refill in a row no summary is made and the turn ends with an error telling the user the context keeps refilling, likely from an oversized file or tool output. ## The compaction request

| id | rule | noeta today |
|---|---|---|
| compact.request.1 | The compaction request is an ordinary main-loop request: same model, same system blocks, same tool list (including deferred tools loaded so far), same thinking, effort and context-management settings, streaming, `max_tokens` 128000. Only the messages change. | covered — `summary.summary_request` reuses the main request (model, system, tools, thinking, `max_tokens`), changing only the messages, the cache mark and the betas (adds `fallback-credit`, drops `afk-mode`). |
| compact.request.2 | The instruction is appended to the end of the conversation as the last user message, never put in the system prompt. When the conversation ends with the user's new prompt, the instruction is an extra text block in that same user message (m3/0009, m3/0017); when it ends with tool results, it is an extra text block after the `tool_result` blocks (m3/0012, m3/0021); after a slash command, it follows the command wrapper blocks (m1/0055). | covered — the instruction joins the last user message that is not a reminder (after results or the command wrapper), never the system prompt (`summary_request`); `make parity` m1/m3 compare the layout. |
| compact.request.3 | The prompt-cache breakpoint is moved to the message just before the instruction (the last assistant message in m1/0055), so the request reads the whole prior conversation from cache (m1/0058 read 21,952 cached tokens and wrote nothing new). | covered — `cache_after=[at - 1]`, the message before the instruction. |
| compact.request.4 | Per-turn `role: "system"` messages already in history (token counters, notifications, environment) stay in place; nothing is stripped or rewritten before summarizing. | covered — reminders and system turns stay in place (`_host_injected`). |
| compact.request.5 | The same instruction text is used for manual `/compact` and for auto-compaction (identical hash in m1 and m3). | covered — one prompt, `prompts/summarize.md`, for `/compact` and auto. |
| compact.request.6 | Which messages are summarized (re-recording r2, seven auto-compactions and a manual one): everything before the newest assistant reply; that reply and what followed it are kept verbatim after the summary (r2 m3/0006, 0014, 0022, 0031; m1/0076 kept the final text reply).
