# Memory v2: policy prompt, frontmatter recall, memory_search, background consolidation

> **Status: Shipped** — the policy prompt, frontmatter recall, `memory_search` and the
> background consolidation agent are live. Durable decisions:
> [memory-consolidation.md](../../adr/memory-consolidation.md).

## Goal

Without changing the Memory v1 substrate (file-per-memory storage, the
`memory_write` / `memory_read` tools, the resident index, automatic recall at the
user-message seam), fill in three capabilities: a **memory policy prompt** (so the
model knows what is worth remembering), a **recall upgrade** (the frontmatter
`description` participates in matching, plus a grep-style `memory_search`), and
**background consolidation** (after a session stops, tidy the memory directory
asynchronously: merge duplicates, archive what has been overturned, backfill what
was missed).

## Non-goals

- **No vector / semantic retrieval.** v1's rule-of-two decision stands (see
  `docs/adr/unified-context-supply.md`, Alternatives #7); industry evidence (the
  file + grep route) supports it too. If it is ever introduced, it goes in as a
  D1-style adapter replacing `match_memories`, unrelated to this spec.
- **No real-time extraction pipeline.** No LLM extracting facts on the message
  path (the Mem0 shape). Memory forms through exactly two channels: the model
  calling `memory_write` inside a session, and consolidation backfilling outside
  one.
- **No change to storage location or the sandbox boundary.** The global directory
  (default `~/.noeta/memories`) and its staying on the host under sandbox mode are
  both untouched.
- **No multi-index sharding, and no cross-agent memory sharing.**
- **No physical deletion.** Both consolidation and the model may only archive
  (traceable); physical deletion is left to a human.

## Context

- Memory v1's design and current state: `docs/adr/unified-context-supply.md`
  ("Memory v1, four parts"); the code is in `noeta.tools.memory` (store + the two
  tools), `noeta.context.memory` (the index resident + `match_memories`), and
  `noeta.execution.memory` (the recall seam).
- Three known v1 gaps: recall matches only on the memory **name**'s tokens (the
  summary does not participate at all); nothing guides the model on **when** to
  write a memory; there is no tidying mechanism, so memories only accumulate and
  never expire.
- Mid-2026 industry convergence (Anthropic's memory tool, Claude Code
  auto-memory, OpenAI Dreaming, Letta MemFS): **file storage + model-managed
  read/write + a small resident index + asynchronous background tidying**. This
  spec brings noeta from "has the substrate" to the full mainstream shape; it
  overturns no v1 decision.
- Research conclusions (benchmark caveats, comparisons between approaches) are
  not recorded here. If a future evaluation is needed, use LongMemEval and run
  the full-context baseline yourself; do not trust LoCoMo numbers.

## Decisions

Two items confirmed with the maintainer:

1. **Spec scope = all three phases.** Phases 1 and 2 can be implemented
   immediately; phase 3 (consolidation) follows the decisions in this spec.
2. **Consolidation trigger = the session-stop seam + debounce.** An interactive
   session has no terminal event (it normally rests at a next-goal `suspended`,
   and `close` is an advisory marker), so the trigger hangs off two existing
   seams — the explicit close cascade and the turn boundary (a completed drive
   returning to `suspended`) — sharing one debounce check: only start the task if
   more than the threshold has passed since the last run (default 24h, recorded
   in a marker). The debounce degrades the turn-boundary trigger into "the first
   turn boundary past the threshold", which is equivalent periodic behaviour with
   zero new scheduling machinery. A timer was rejected (an idle deployment would
   still wake); purely manual was rejected (automatic tidying would then never
   happen). The marker is written at enqueue time, so a slow run cannot
   re-trigger itself.

The following are engineering decisions taken per repository convention (not
re-confirmed at implementation time):

3. **Frontmatter is optional, generated from params, and backward compatible.**
   `memory_write` gains optional `description` (a one-line summary) and `type`
   (enum `user | project | procedural | reference`); the tool assembles the YAML
   frontmatter (`key: value` inside a `---` fence) so the model never writes the
   fence by hand. If `text` already carries frontmatter and no params were passed,
   it is accepted verbatim. Parsing uses a minimal parser confined to
   `noeta.tools.memory` (it recognises only `key: value` lines inside the fence);
   **no yaml dependency is introduced**. Old files without frontmatter behave
   exactly as before (the first line is the summary).
4. **Index entries widen to a 3-tuple, description first.**
   `MemoryStore.entries()` yields `(name, summary, type)` (`type` defaults to the
   empty string); `summary` takes the frontmatter `description`, falling back to
   the first line (skipping the fence). The index renders `- name (type): summary`
   when a type is present, and otherwise stays byte-identical to v1's
   `- name: summary`. The `MemoryEntries` alias widens to the 3-tuple in step — it
   is confirmed not to be publicly exported through `noeta.sdk`, so the ripple is
   confined to internal iteration points and tests. `match_memories`' signature is
   unchanged, and the type field never participates in matching.
5. **Recall matching upgrades to two tiers, staying deterministic.** Name-token
   matching (≥1 token intersection, the status quo) takes priority; summary-token
   matching then fills in behind it, **requiring ≥2 distinct token intersections**
   (a single token is too noisy). Within each tier, index order is preserved; the
   total remains capped by `DEFAULT_RECALL_MAX_HITS`. Pure function, zero IO.
6. **Search = a new `memory_search` tool, not an overload of `memory_read`.** A
   single-purpose schema is more stable for the model, and `read`'s name-only
   contract stays put. Semantics: case-insensitive **substring** matching (no
   regex in v2), scope = name + full text, grep-style output (at most 3 matched
   line excerpts per memory, at most 10 memories, deterministic ordering), and it
   does not search `archive`. `MemoryStore` gains `search()`; the tool joins the
   `build_memory_tools` pack with `risk_level="low"`.
7. **Expiry = a `memory_archive` tool + an `archive/` subdirectory.**
   `MemoryStore.archive(name)` moves the file into `root/archive/`; `entries()`'
   non-recursive `*.md` glob naturally excludes subdirectories, so the index and
   recall stop seeing it automatically. The new `memory_archive` tool
   (`risk_level="medium"`) joins the pack — the interactive agent (the user says
   "that one is out of date") and the consolidation agent use the same knife.
   Archiving the same name twice uses a numbered suffix to avoid overwriting.
8. **The policy prompt rides the preset prompt layer, not the index resident.**
   The index renderer has zero footprint on an empty store (a byte-stability
   property worth keeping), whereas the policy has to be present **before the
   first memory is ever written** — so it cannot ride the index. Instead: a new
   prompt fragment (its own file under `presets/prompts/`), pulled into `main`'s
   prompt and also exported as a public constant so authors of custom specs
   (`memory=True`) can concatenate it themselves. The policy has three parts: what
   is worth remembering (user corrections, cross-session project facts,
   procedural experience, pointers to external resources) / what is not (anything
   the code or git already records, anything that only matters to this session) /
   check for duplicates before writing (update an existing memory rather than
   adding a second one; archive the stale).
9. **Consolidation is an ordinary agent whose tool surface is the memory pack, no
   fs / bash.** An internal preset (not in the user-selectable list) whose goal
   carries a host-exported "session excerpts since the last tidy" digest (read the
   text blocks of `MessagesAppended` from the ledger, the most recent N sessions,
   each truncated at M tokens, with a ceiling so it cannot blow up). Its duties are
   only three: merge duplicates (write the merged file + archive the originals),
   archive what has been overturned, backfill what was clearly missed. The number
   of operations per run is capped. Writes are naturally confined to the memory
   directory by the slug constraint.
10. **The debounce marker is `.consolidation-state.json` under the memory
    directory** (not `.md`, so the index never sees it), recording the last run's
    timestamp. The trigger point is the session-stop seam in the noeta-agent
    backend; the threshold is configurable, default 24h.
11. **Layered switches, isomorphic to instructions: consolidation does not enter
    `Capabilities`.** It is host behaviour, not agent identity — a noeta-agent
    product-layer config item (default: on when memory is on; an env var can turn
    it off), with the SDK exposing an explicit entry function for hosts that
    orchestrate it themselves. `Capabilities.memory` remains the master memory
    switch.
12. **Two concurrency / freshness weak-consistency effects are accepted and
    documented.** (a) Consolidation writing concurrently with an active session:
    file-per-memory makes the conflict surface a single file, last-writer-wins,
    and consolidation re-reads the original before rewriting it. (b) A running
    session's index resident is a snapshot taken at wiring time and is not
    refreshed after consolidation (the `evolving` policy already permits hash
    drift); the recall path reads from disk and so is immediate, and a new session
    picks up the new index.
13. **Long-term documentation:** consolidation's trigger / execution / expiry
    semantics are long-term trade-offs, so add
    `docs/adr/memory-consolidation.md`; update `CONTEXT.md`'s Memory entry to the
    v2 four channels (the write tool / the policy prompt / recall + search /
    consolidation). The term is fixed as **consolidation** (the colloquial
    "dreaming" appears once in the ADR, as a comparison).

## Implementation plan

### Phase 1 — policy prompt + frontmatter + recall upgrade (purely additive, ship first)

1. `noeta.tools.memory`: the minimal frontmatter parser (`key: value` inside the
   fence); `_first_line_summary` → `_entry_summary` (description first);
   `MemoryStore.entries()` also yields the type (widen the internal tuple or add a
   companion accessor, whichever avoids changing the public `MemoryEntries`
   shape — the rendering layer needs the type, the matching layer does not);
   `MemoryWriteTool`'s schema gains optional `description` / `type`, and `invoke`
   assembles the frontmatter.
2. `noeta.context.memory`: `render_memory_index_text` supports the `(type)`
   annotation; `match_memories` gains the two tiers (name ≥1 / summary ≥2), with
   the cap and ordering semantics written into the docstring and the contract
   tests.
3. `presets/prompts/`: add the memory policy fragment; pull it into `main`'s
   prompt; export the constant; update `docs/reference/` accordingly.

### Phase 2 — memory_search + memory_archive

4. `MemoryStore.search(query)` (case-insensitive substring, deterministic
   ordering, line excerpts) and `MemoryStore.archive(name)` (move into
   `archive/`, anti-overwrite suffix).
5. The new `MemorySearchTool` / `MemoryArchiveTool`, joining
   `build_memory_tools`; update `docs/reference/tools.md` and its zh mirror.

### Phase 3 — consolidation

6. Ledger excerpt export: a host-side function turning the session list since the
   marker's timestamp into per-session message text excerpts (delimited,
   truncated).
7. The internal consolidation preset (memory pack only) + the run entry point (an
   explicit SDK function).
8. noeta-agent backend: hang the trigger on the session-stop seam (read the
   marker, apply the debounce, start consolidation through the background subtask
   mechanism, write the marker on success); product-layer config item + env
   switch.
9. `docs/adr/memory-consolidation.md` + the `CONTEXT.md` Memory entry + the
   release changelog.

- Parallel split: T1+T2 on one track, T3 on one, T4 on one, and T5+T6+T7 on one
  track once the first three have merged.

## Acceptance criteria

1. **Compatibility:** for existing memory files without frontmatter, index
   rendering, recall and `read` are byte-identical to v1; an empty store still has
   zero footprint (all existing contract tests green).
2. **Frontmatter:** a file written with `description` / `type` shows the
   description in its index line (with the type annotation); `memory_read` returns
   the full text including the frontmatter.
3. **Recall:** a name hit outranks a description hit; a single-token description
   intersection does not fire; same input, same output (deterministic); the cap
   takes effect.
4. **Search / archive:** `memory_search` hits substrings in both name and body,
   emits line excerpts, and excludes archived content; after `memory_archive` the
   memory disappears from the index and from recall, and the file exists under
   `archive/`.
5. **Consolidation:** a session stops past the debounce threshold → the background
   task runs and uses only the memory tools; duplicates are merged (originals go
   to archive), overturned memories are archived, and the marker is updated;
   inside the threshold nothing fires; with the switch off, zero behaviour.
6. **Red lines:** no new IO on the compose path; all new content still enters
   context ledger-first (consolidation injects into no active session).
7. `make check` fully green; items 1–5 each covered by a contract test.

## Risks

- **Description matching adds recall noise:** the ≥2-token threshold is a guessed
  initial value. If noise is still high, tighten to ≥3 or require one uncommon
  word — do not escalate to semantic retrieval.
- **The consolidation agent archives something wrongly:** the duties prompt must
  be conservative ("when unsure, do nothing"); the operation cap plus archive
  being reversible are the backstop; early on, add a run log in noeta-agent so a
  human can spot-check.
- **Ledger excerpt volume:** with many long sessions, a badly tuned excerpt cap
  makes consolidation expensive. Start N/M conservative (e.g. 10 sessions ×
  4k tokens), configurable.
- **The semantics of the session-stop seam:** in the served product, "session
  ended" may present as idle rather than an explicit close. Before implementing
  T7, confirm the exact hook point for the stop event in the backend
  lifecycle/engine_room; if only idle semantics exist, use an idle timeout as the
  trigger.
- **Ripple from widening the `MemoryEntries` shape:** the rendering layer wants
  the type and the matching layer does not. If widening the tuple would disturb
  existing signatures, prefer a companion accessor and avoid gratuitous breakage.
