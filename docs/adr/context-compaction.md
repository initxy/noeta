# Context compaction: a token-only trigger, real recorded usage converted into the estimator's unit, and a protected verbatim tail

## Context

A long session outgrows the provider's context window. Three invariants constrain any answer: events are immutable (see event-sourced-truth.md), state is folded deterministically from the event log, and the mechanism is provider-neutral (see provider-neutral.md). Compaction may therefore never re-read disk and never count tokens live — every number it uses has to be one that is already recorded, so a live run and a resumed run derive the same boundary from the same history.

## Decision

- **The token gate is the only entrance.** Compaction fires when the size of the pending request reaches the usable window (`context_window − max_output_tokens − a fixed buffer`). A message-count tail window exists as an explicit, off-by-default escape hatch and is not part of the normal path; when engaged it records its own selection provenance.
- **Trigger size mixes the last recorded real input count with an estimate of what was appended since**, then takes the larger of that and the pure estimate, so the mix can only raise the reading and never mask a genuinely huge raw history. The baseline is the count that came back with this Policy instance's own last main round-trip, falling back to the value fold projects onto the Task; with no recorded count at all, the trigger is the pure estimate. The summarize round-trip measures a different request and never becomes the baseline.
- **A compaction invalidates the baseline.** Once the prefix collapses, every recorded count in hand describes a history that no longer exists, and trusting it would re-fire the trigger on a just-shrunk history whose boundary can no longer advance. fold zeroes the projected count when it applies a compaction — the same value a fresh Task carries — so each consumer's existing "no baseline yet" fallback covers the post-compaction step with no extra branch.
- **The LLM client folds each event it emits onto the Task being stepped**, through a callback the Engine supplies on the step context. The Engine stays the sole physical writer; without this the recorded counts only reach the Task at the next lease boundary, so inside one tool loop every consumer of the baseline silently degrades to the raw estimate.
- **Real-token knobs are converted into the estimator's unit by an observed density.** The window and the tail budget count real provider tokens; the summary-boundary walk and the composer's prune walk accumulate a chars-per-token heuristic. Density is the ratio of the two on the last recorded round-trip — both already-recorded numbers — and is `1.0` until one exists and after an invalidating compaction, which reproduces the unconverted arithmetic exactly. Both layers apply it.
- **Compaction has two layers sharing one water mark.** The micro layer is the composer's tail prune: it clears tool-result output older than the tail budget to a marker while keeping the block's identity and success flag, and it opens only once the request approaches the usable window, so a half-empty window never forces the model to re-read what it already fetched. The macro layer is the summarize round-trip. The prune gate reads the larger of the estimate and the real baseline; it has no analogue of the trigger's "appended since" term, so it opens at most one round-trip late — the safe direction, since the summarize trigger backstops it while opening early would clear output the model still needs.
- **The cleared marker is lean** — it says the output was elided and nothing else. The full body stays dereferenceable off-prompt: a pruned body through the context plan's cleared-output refs, an over-threshold inline truncation through the ref on the recorded tool result.
- **A verbatim tail is protected.** A third of the usable window is kept word-for-word and only the older prefix is summarized. The tail is strictly smaller than the window, so a triggered compaction always has a non-empty prefix to collapse.
- **The summary is a fixed set of sections**: original intent, key technical concepts, relevant file paths, errors and fixes, all user messages, pending tasks, decisions and constraints. There is deliberately no "current work" or "next step" section, and the file section carries paths only — never file bodies. The wording names no vendor and no vendor-specific mechanism.
- **Safety and permission constraints are re-inserted verbatim.** After the model returns a summary, a deterministic post-check over the same collapsed prefix appends back, word for word, any constraint the model dropped or paraphrased.
- **The passive overflow path is the backstop.** When the provider itself returns an over-limit error, compaction runs and the request is retried rather than failed.
- **Compaction fails closed rather than spinning.** A trigger whose new boundary would not strictly advance past what is already collapsed fails the step outright, and an errored or empty summarize response fails the step instead of replacing the prefix with an empty note. fold separately latches a thrashing flag when several compactions land within a few turns of one another.

## Rationale

- **Everything the mechanism reads is already on the event stream**, so the boundary, the density, and the prune cutoff are all deterministic functions of recorded history. Reading a recorded count back is not the same as counting live; only the latter would break resume.
- **The verbatim tail exists because compose cannot re-read disk.** A stance that keeps no verbatim text depends on backfilling current file contents at compaction time, which determinism forbids. The tail is the highest-fidelity record of recent state, always more trustworthy than a summary line restating it.
- **The unit conversion is what keeps the two layers honest.** The window and the tail budget count real tokens while both walks accumulate a heuristic; the two coincide only while the heuristic is accurate. A dense payload — mixed scripts, JSON structure, base64 thinking signatures, tool schemas — measures far below the assumed characters per token, and a heuristic accumulator compared against a real-token tail budget then protects a "tail" the whole history fits inside: the boundary cannot advance and a legitimately triggered compaction fails. Correcting one layer alone is worse than correcting neither, because it breaks the accidental symmetry that made both sides wrong in the same direction.
- **The baseline belongs to Task state, not to a Policy.** The invalidation rule is a property of the history, so every reader needs it and a resume has to re-derive it. A second consumer cannot reuse a Policy-private workaround, and a third would need a third one.
- **A smaller tail makes compaction fire less often, not more.** After a compaction the live context is the summary plus the tail, so a smaller tail leaves more headroom before the next trigger; each summary simply covers a bigger prefix.
- **A cleared marker must be lean but not empty.** The model has no tool that dereferences a content hash — it recovers omitted content by re-running the tool or re-reading the path — so a hash in the prompt is wasted tokens at best and an invitation to hallucinate a fetch capability at worst. An empty string is worse still: it reads as "the tool returned nothing".
- **Keeping only paths in the summary is the honest option.** Re-reading disk breaks determinism, and dereferencing a stored snapshot hands stale bytes to an agent that is actively editing that very file — worse than handing it nothing. The model re-reads the current version when it needs it.

## Alternatives considered

1. **Drive compaction from a message-count gate.** Rejected: a count is decoupled from tokens, so it fires far earlier than the token gate and bluntly drops early context — including the original requirement — before the summarizer ever runs.
2. **Trigger purely on the character heuristic, with no real-usage baseline.** Rejected: with counting as the only gate its accuracy is the whole mechanism, and the provider's real count is already in the event stream, so using it costs nothing in determinism.
3. **Retune the characters-per-token constant instead of measuring density.** Rejected: a new constant only moves the bias, and it changes every estimate ever produced — a composer version bump that breaks equality with existing recordings.
4. **Keep the density correction inside the Policy.** Rejected: it leaves the composer's prune valve reading the rejected estimate, so the relief valve never opens and the summarize call becomes the only relief a long session ever gets.
5. **Keep baseline invalidation as a Policy-private sentinel.** Rejected: the rule describes the history, not one consumer, so it has to survive a resume and be visible to every reader.
6. **Summarize nearly everything and keep no verbatim tail.** Rejected: that only works with disk backfill, which determinism forbids; without it the safety buffer of recent verbatim state disappears.
7. **Protect half the usable window as the tail.** Rejected: heavier than needed once the summary keeps file paths and the model re-reads the current version on demand. A third frees window for actual work at a bounded cost in recent verbatim fidelity.
8. **Include "current work" and "next step" sections in the summary.** Rejected: they restate, from an estimate, text that already sits verbatim in the protected tail — wasteful and liable to disagree with it.
9. **Build a separate standalone micro-compaction layer.** Rejected: the composer's tail prune already is one, and it is more continuous than a second scheduled pass would be.
10. **Backfill file bodies into the summary, from disk or from stored content.** Rejected: re-reading disk breaks determinism, and stored bytes are stale for the file most likely to matter.
11. **Drop a spent tool round-trip entirely once its output is cleared.** Rejected: with large arguments already offloaded and the output already cleared, what remains inline is the tool name, a small argument and the envelope — a few dozen tokens per pair, against the real cost of losing the call record from a segment that has not been summarized yet.
12. **Use a provider's own server-side context management, or fork a session to reuse its prompt cache.** Rejected: vendor-specific mechanisms break provider neutrality, and the summary wording has to stay portable.

## Consequences

- The trigger, the summary boundary, the summary template and the verbatim-constraint post-check live in the `react` built-in's Policy; the neutral estimator is `noeta.protocols.token_estimate`; the window and tail derivation is in the `providers` built-in, typed by the compaction config in `noeta.execution.builder`.
- The relief valve, the lean marker and the cleared-body provenance live in `noeta.context.composer`, with the cleared-output list on `noeta.protocols.context_plan`; inline over-threshold truncation is in the core decision handlers. The baseline projection, its invalidation and thrash detection are in `noeta.core.fold`, and the apply channel the LLM client uses is on `noeta.protocols.step_context`.
- The composer version identifies the composed *structure*. Changing when the valve opens, or how large the protected tail is, does not bump it; changing the estimator or the assembled shape does.
- No part of compaction may read disk or ask a provider to count tokens. Anything a future change wants to base a decision on must first be a recorded number.
