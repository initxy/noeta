# A mid-step crash is recovered per attempt: seal it with a snapshot-shaped marker, re-drive automatically when the approval surface proves it safe, otherwise park the task for a human

## Context

A worker crash mid-step — `kill -KILL`, power loss — leaves a **partial-step orphan**: the folded status is `running`, but the live wake window ends in a half-finished decide→act attempt with no reachable suspend or terminal. One Step is a loop of such Attempts, and every attempt's first durable emit is `ContextPlanComposed`, so the stream carries an implicit attempt journal: an attempt's identity is that event's seq, its intent is the plan plus the decision events after it. What the journal does not supply is a durable **abandon** record and a recovery posture.

Two failure modes bound the design. Silently terminating the task throws away work a human could have salvaged. Silently re-driving a dirty window duplicates side effects that happened once. Recovery must close both without changing dispatcher schema or wake-delivery semantics.

## Decision

- **Recovery is classified-automatic.** An interrupted attempt whose recorded activity is provably side-effect-safe is sealed and re-driven with no human involved; an attempt with unprovable side effects is sealed and the task is durably **parked** for a human decision. Never silently terminal, never silently duplicated. The seal records why: `auto_redrive`, `unsafe_tool_activity`, `interrupted_approval`, or `abandon_cap`.
- **One classification rule: whatever could run without a human approval gate may be re-driven without a human.** Pure record events — plans, LLM request records, assistant messages, state patches, compaction — are always safe. Every recorded tool call, started *or* finished (a re-drive re-decides and may re-execute a finished call), is fed with its recorded arguments through the live guard chain: permission mode, risk ceiling, `can_use_tool`, skill grants — the same surface that gates live execution. Any non-ALLOW verdict means a human: an approval requirement obviously, but a deny too, because the call's side effects happened once and only an operator can judge them. A gate-free permission mode therefore classifies every attempt safe, and whatever a mode auto-approves classifies safe. A spawned subtask in the window, an unknown tool name, and a guard resolution failure all classify as needing a human — the classifier fails closed. Classification runs against the **pre-attempt baseline**, the same bounded fold the seal serialises, not the dirty full stream: the question is whether the re-drive, which runs on the sealed state, could proceed unattended, and folding the interrupted window's own activity into the budget and repetition counters would park attempts the re-drive itself would allow.
- **The seal is a marker event plus a snapshot re-base, not a journal table.** `StepAttemptAbandoned{abandoned_from_seq, state_ref, reason}` scopes the rewind to one attempt: recovery folds the state to just before the interrupted attempt's anchor event, serialises it into the ContentStore, and appends the marker. fold treats the marker exactly like a rewind — an in-stream rebuild baseline, a member of the snapshot-baseline event set — so the partial attempt becomes folded-over dead history that stays on the stream and stays auditable. The dispatcher is untouched, and the payload is a few hundred bytes, far under the payload cap.
- **Only the interrupted attempt dies.** The baseline is the folded state just before that attempt's anchor: its `ContextPlanComposed` (the last one in the live wake window), or, for a plan-less approval window, its first activity event. Attempts completed before it — plan, decision, fully paired tool starts and finishes — remain live history: their side effects are not re-executed and their results are not re-computed. Prelude events precede the first `ContextPlanComposed`, so the user's message survives automatically.
- **The case sentinel is `ContextPlanComposed`, not "any event after the wake".** The worker's woken reconciliation on a `running` status keys on whether an attempt started. None means run the bare step, which is correct by construction for every caller — timer and subtask re-deliveries, seeded command wakes whose prelude is durable, and a crash that fell between a seal and its re-drive. One present means the recovery machine: classify, seal, then re-drive under the same lease or park. The drained branch scans identically before stepping, so a dirty window cannot be re-driven silently there either. One orphan shape is plan-less by construction: an **interrupted approval execution**, where the drive-side approval prelude executes the approved tool before the step's first plan, so a crash there leaves an approval resolution and a tool start with no plan. The scanner anchors that attempt on its first activity event, and recovery **always parks it, never re-drives** — a human is in that loop by definition, and duplicating an approved side effect without asking is exactly what recovery exists to prevent.
- **Append-only preludes are durable at seed time.** Preludes that only append events — a goal message, an answer, a chained model binding — are applied synchronously on the request thread, so the wake note and the prelude events land before the acknowledgement. The acknowledgement therefore means "your input is durable", and the drive enters the woken machine prelude-less, on the bare-step path. Both lease-acquisition paths share one seed tail, so the promise cannot depend on which path produced the lease. A prelude failure after the wake note compensates by re-suspending on the command's own handle and releasing the lease, so the conversation stays resumable and a client retry works, instead of stranding a half-seeded `running` window a worker would later re-drive without the input. The seed resolves the Engine *before* applying the prelude and pins it on the seeded turn, so a seed-written model binding keeps its drive-the-next-turn semantics; the accepted divergence is that a crash re-drive of a model-switch turn re-resolves from the log and runs on the newly bound model. The approval prelude is drive-side because it *executes* the approved tool and must not block the request thread; a crash before its resolution lands is benign — the task re-suspends on the same approval and the operator approves again — and a crash *during* the approved execution is the plan-less window above, which parks.
- **A park is a stopped conversation.** Under the recovery lease: seal, append one system-origin notice naming each interrupted call and whether it completed, suspend on the next-goal wake handle, release suspended and consume the wake. The parked task behaves exactly like a conversation someone stopped: it shows as suspended with the notice, typing a message resumes it from the clean baseline, and close and cancel work as they do anywhere else. There are no new API verbs and no new UI forms. The one variation: an interrupted approval execution re-suspends on the window's **own** approval handle instead of the next-goal handle. Pending approvals are folded state, so the seal restores the pending approval and the ordinary approve and deny verbs work; the operator re-approves after reading the notice. An automatic re-drive, by contrast, is silent — injecting a notice would perturb every recovered transcript for no benefit, so the park notice is the only transcript change recovery ever makes.
- **Repeated crashes recurse, capped at three consecutive seals in a window.** The seal is deliberately not a wake-window boundary for the woken matcher, so a crash during a re-drive re-enters recovery: before the seal as a fresh recovery case, after an `auto_redrive` seal as a bare re-drive (the seal re-based the state), and after a park-reason seal as a park *completion* — the reason recorded in the seal is the durable "do not re-drive" decision, so the remaining writes (the notice, skipped when it is on the stream; the suspend; the release) finish under the fresh lease rather than a bare step running over them. Blockers for a re-appended notice are re-derived from the sealed dead tail. Past the cap, recovery seals with reason `abandon_cap` and parks regardless of classification — the crash-loop backstop, mirroring the dispatcher's stale-reclaim cap. When a plan-less approval window and the cap coincide, `interrupted_approval` wins the reason: the notice must tell the operator a human-approved call was interrupted, whatever the seal count.

## Rationale

- **Classified-automatic is the only posture that closes both failure modes at once.** The overwhelmingly common orphan — a read-only or plan-only window — needs no human judgment, and a purely manual posture spends operator attention on it. The actual hazard is duplicate side effects, and that is exactly what the classification isolates: automate everything below the approval line, stop dead above it.
- **The classification borrows an already-trusted boundary instead of inventing a second safety vocabulary.** "Would this call run unattended live?" is a question the guard chain answers for every tool call, so recovery can never be more permissive than live execution. The corollary is the same trust surface including its edge: a side-effectful custom tool left at the default low risk level classifies as safe — but such a tool runs unattended live too, so this is not extra exposure. Authors of side-effectful custom tools declare a higher risk level.
- **The classification is self-consistent with how a window gets orphaned.** A plan-anchored attempt can only contain tool calls the guard allowed unattended — an approval-needing call would have suspended the window rather than orphaned it — so plan-anchored attempts are auto-redriveable almost by construction. The parks are the degenerate cases: guard configuration that differs between the original run and recovery, a spawn in the window, a guard resolution failure. The windows with a human's risk in them are exactly the approval executions, which always park.
- **A marker plus a snapshot re-base reuses the whole rewind machinery and touches no hardened surface.** The attempt journal exists implicitly; one snapshot-shaped event supplies the missing abandon record while inheriting the fold reset, the baseline-set lookup, and the bounded point-in-time fold wholesale. The marker is a lease-checked append written under the recovery lease, so a zombie step thread surviving the crashed process cannot race it, and nothing in the machine assumes a worker count.
- **Seed-time preludes turn an ordering promise into a durability promise.** Writing the prelude on the request thread is what makes the bare-step path *provably* correct rather than correct-for-known-callers: no window can reach a worker with the acked input unwritten.
- **Park-as-stopped-conversation costs nothing to learn or build.** The suspended-on-next-goal shape exists for a human stop, so a parked task inherits resume, close, and cancel for free, and the notice does double duty: the human reads it while the task rests, the model reads it when the conversation resumes.

## Alternatives considered

1. **A dispatcher-side attempt journal table.** Rejected: it puts recovery state into the dispatcher — one more mutable state replay must reproduce — and cuts into the hardened wake-recovery surface, for state derivable from the stream.
2. **Whole-window abandon, re-basing to the turn boundary.** Rejected: it re-executes completed attempts' side effects, re-computes their results, and throws away the turn's prelude events, so the user's message dies with the window. Attempt granularity keeps all of that live for the price of one bounded fold.
3. **Wake-event-carried command intent** — putting the command payload into the wake event so a re-delivered wake replays it. Rejected: it grows dispatcher-held wake state into a second carrier of conversation content, needs its own dedup story on re-delivery, and violates the single-truth rule that user input lands in the EventLog and nowhere else. The seed-time write gives the same durability with no shape change.
4. **A manual posture with better tooling** — a typed error plus inspect and re-drive verbs. Rejected: it leaves acked-input loss unaddressed, imposes operator work on the common all-safe window, and adds a verb surface for a decision the recorded data answers.

## Consequences

- Protocol and fold: the abandon payload lives in `noeta.protocols.events` with its restore mapping in the storage payload registry; the fold reset it shares with a rewind lives in `noeta.core.fold`; the snapshot-baseline event set is defined once in `noeta.protocols.event_log` and consumed by every EventLog adapter's latest-baseline lookup and by the bounded log. Each adapter's partial fold-baseline index predicate is a frozen literal pinned in sync with that constant by a query-plan test, so widening the set requires a new migration that re-creates the index — a partial index is only chosen when its predicate matches the query exactly.
- Runtime: the pure attempt scanner, the classifier, and the abandon cap live in `noeta.runtime.attempt`; the seal / re-drive / park machine, the case sentinel, and the drained-branch routing live in `noeta.runtime.worker`; the lease-checked seal append and the classifier's guard predicate live in `noeta.core.engine`. Seed-time prelude application lives in `noeta.execution.driver`. A trace exporter segments the task trace at the seal exactly as it does at a rewind.
- Costs and limits: the seed lengthens a command's request path by a few bounded appends; recovery prevents silent *duplicate* execution but compensates nothing — inspecting what a crashed side-effectful call actually did stays the operator's job, and the park notice says exactly that; a model-switch turn re-driven after a crash runs on the newly bound model.
- Recovery always runs under a lease and its seal is a lease-checked append, so whatever fences leases fences recovery too; nothing in this design assumes a single worker.
