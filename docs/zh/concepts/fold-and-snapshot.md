# Fold 与快照

**fold** 是把 EventLog 还原为 Task 状态的函数。它的输入被刻意保持最小——`fold(event_log, content_store, task_id)`，别无其他。没有时钟、没有随机性、除这两个存储之外没有外部 IO，它也从不重新调用一个 provider。这种纯粹性换来了一个具体能力：同一条日志，在任何机器上的任何进程里 fold，都产出**字节级相同的状态**。

正因如此，恢复根本没有任何专门的"加载状态"逻辑。要恢复一个挂起的 Task，就 fold 它；要在宿主 UI 里渲染它，就 fold 它；要事后审计它，还是 fold 它。状态永远是一个计算得出的投影，而不是一个必须与日志亦步亦趋保持同步的单独存储副本——"副本与日志不同步"这一整类 bug 也随之消失。

## 两条路径，一个结果

从顶部 fold 整条日志会让长任务越来越慢，因此 fold 保留一条基线快速路径：

- **从顶路径** —— 从 `TaskCreated` 创世事件引导出空状态，然后重放一切。
- **基线路径** —— 从最新的基线事件恢复状态，然后只重放它之后的尾部。

一个基线是一个携带指向 ContentStore 的 `state_ref` 的普通事件。有四种类型符合资格：`TaskSnapshot`、`TaskRewound`、`StepAttemptAbandoned` 和 `TaskForked`。`TaskSnapshot` 是纯粹的加速——Engine 会在每个终止事件之前、每次挂起之前，以及当连续工具调用轮次越过 `CONSECUTIVE_TOOL_CALLS_SNAPSHOT_THRESHOLD`（20）时在循环中途各写一个，因此一个从不让出的 Policy 仍然会留下一个可用的恢复点。另外三种是有意义的重定基（re-base）标记，fold 在*两条*路径上都会应用它们：一个被回退的对话、一个被放弃的步骤 attempt，以及一个被派生（fork）的任务，都是命名一个新基线，而不是编辑此前发生的内容。

一条铁律凌驾于两条路径之上：**它们必须 fold 出字节相等的状态**。`fold(..., ignore_snapshots=True)` 会强制完整重放，测试用它来交叉校验。这条规则把 `TaskSnapshot` 的地位钉死为一个性能加速器，永远不是第二个事实来源：把它们逐个删光，行为不变，只是变慢。

同样的优先级也处理 fold 无法信任的状态。一个缺少 fold 所依赖字段的基线正文会被丢弃，转而做一次完整重放，直到一个新写入的基线重新激活快速路径。宁可慢，不可错。

## 规范化渲染

"字节相等"需要一个后盾，这一层就是 **canonical**（规范化）：把任何类型化值渲染为一种稳定的字节形式——键排序、分隔符紧凑、全程 UTF-8 的 JSON。等价的对象因此渲染为完全相同的字节，同一内容的哈希在任何机器、任何时间都相同。内容寻址依赖 canonical 来去重，基线正文也往返穿过它，好让带标签的值类型（`ContentRef`、唤醒条件、子任务结果、类型化消息块）在跨越边界时保持自己的身份。整个事件溯源设计的可复现性就建立在这一薄层之上。（随着字段的增删，记录如何保持可 fold，在[架构概览](../architecture/overview.md)中有说明。）

## fold 何时运行

每次唤醒、每次检查，以及每一个租约步骤的开始。一次时间点读取——"这个任务在 seq N 时是什么样子？"——是通过对同一批事件的一个有界只读视图来 fold，而不是给 fold 教一个上限。它只向前 fold：流上没有任何东西会被改写。
